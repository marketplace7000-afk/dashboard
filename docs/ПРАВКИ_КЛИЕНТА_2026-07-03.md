## Вопрос 3. Откуда считается «Маржинальная прибыль» (карточка сверху, 582 080,499 ₽)

**Цитата клиента:** «Откуда считается эта маржа?»

**Это не значение из одной ячейки листа — это сумма, посчитанная платформой.** Формула (код: `src/components/LiveOzonRoi.tsx`, блок `aggregate`, строки 170-214):

1. Берутся только товары, у которых **есть заказы за выбранный период** (сейчас «7 дней (26.06-02.07)», данные заказов — из аналитики Ozon).
2. По каждому такому товару берётся его «Прибыль · всего» — то же число, что в колонке таблицы ниже (для товаров из листа «Маржа» это колонка R «Маржа после вычета налога по артикулу за неделю»; если товара нет в листе — платформа досчитывает сама: прибыль/шт × кол-во заказов).
3. Все эти числа по товарам складываются → получается 582 080,499 ₽.
4. ROI 30.1% рядом — это (сумма прибыли) ÷ (сумма себестоимости проданных штук) × 100. Себестоимость штуки берётся тоже из листа (колонка K), кол-во штук — из заказов Ozon за период.

**Важный нюанс, который стоит держать в уме:** «Прибыль · всего» из листа — это прибыль финансиста **за его последнюю занесённую неделю** (сейчас неделя 26), а не строго за даты «26.06-02.07», которые показывает платформа (это окно для заказов из Ozon-аналитики). Если неделя финансиста по датам не 1-в-1 совпадает с окном «последние 7 дней», сумма может слегка разъезжаться. Обе цифры (прибыль из листа и заказы за 7 дней) — верные каждая по-своему, но считаются по немного разным временным окнам. Пока это не баг, а особенность объединения двух источников (лист обновляется раз в неделю, дашборд — каждый день). Если для клиента это критично — можно либо ограничить сумму строго датами листа, либо явно подписать это разночтение в интерфейсе. Ждём: важно это или нет.

**Статус: РАЗЪЯСНЕНО.** Действий не требует, если клиент не попросит поменять логику объединения периодов.

## Вопрос 5. Можно добавить ссылки на конкурентов в блок сравнения цен (Ozon)?

**Почему нет напрямую:** этот блок считается из метода Ozon Seller API `v5/product/info/prices` → `price_indexes` (`ozon_index_data`/`external_index_data`/`self_marketplaces_index_data`). **Как можно сделать альтернативно:** в проекте уже существует отдельный, независимый механизм — поиск по витринам WB и Ozon (`api/_lib/competitors.ts`, эндпоинты `/api/competitors/search` и `/api/competitors/card`). Пример из скрина явно это подтверждает: **CP-KVDRT-PLUS** — «моя цена» 30 000 ₽ против «внешн. min» 1 331 ₽ (разрыв −95,6%). Аналогично подозрительны **OTTOCAST-P3-KRUG** и **OTTOCAST-P3-KVDRT** (по 20 000 ₽ «моя цена», разрыв −83-84%) — круглые завышенные числа похожи на артефакт того же класса, что уже чинили в Правке 2 (там же Ozon отдавал «150 000 ₽» вместо реальных 28 325 ₽).

**Плюс отдельная находка — этот блок НЕ фильтруется по «товары в наличии»:** остальная часть раздела «Акции» (таблица выше) показывает только товары в наличии (это была правка по итогам созвона 01.07). А «Возможные акции конкурентов» строится из `rows` — ПОЛНОГО списка 84 товаров кабинета, без фильтра по остатку. То есть сюда могут попадать архивные/распроданные позиции.

**Что сделать (по аналогии с решением из Правки 4):**
1. Раз источник (индекс Ozon) уже признан ненадёжным для похожей задачи — либо (а) добавить фильтр разумности перед показом строки (например, не показывать разрыв больше определённого % — отсекать явный мусор), либо (б) как обсуждали в Вопросе 5, подключить реальный поиск по витринам WB/Ozon вместо непрозрачного индекса, либо (в) убрать блок совсем, если он больше запутывает, чем помогает.
2. Независимо от решения по источнику данных — добавить фильтр «только товары в наличии» (использовать `inStock`, а не `rows`), чтобы хотя бы не путать с архивными позициями.
3. Переименовать блок честнее: не «акции конкурентов» (это не факт акции), а что-то вроде «Мы дороже минимума по рынку (по данным Ozon)» — с пометкой, что источник не всегда точен.
