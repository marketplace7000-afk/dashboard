# Парсер конкурентов (WB + Ozon) — как делаем и как работает

Документ описывает архитектуру парсера конкурентной выдачи для Auto Vibe.
Цель: показывать карточки конкурентов по поисковому запросу (цена, рейтинг,
отзывы, фото) и не попадать под баны площадок (429 / антибот).

Контекст рантайма: один долгоживущий Node-процесс на московской VM
(`server.ts`), in-memory + дисковый кэш (`api/_lib/cache.ts`), фоновый
сборщик (`handleCron`). РФ-egress — площадки видят российский IP.

---

## 1. Что уже есть (база)

### WB — работает
- `GET /api/wb-public/search?q=<запрос>&limit=<n>` → `handleWbPublic` в
  `api/route.ts` → публичный `https://search.wb.ru/exactmatch/ru/common/v9/search`.
  Возвращает топ выдачи по «популярности». Без токена.
- `GET /api/wb-public/card?nm=<nmId>` → `card.json` с `basket-XX.wbbasket.ru`
  → описание, характеристики, все фото.
- Парсинг защищён от HTML-429 (`looksHtml` / `is429`), кэш 90 мин на запрос.
- Дальше карточка уходит в Claude Vision (`aiCardAudit`) и сравнение
  (`aiCompetitorsSummary`).

### Ozon — НЕТ парсинга выдачи
- Есть только **индекс цен Ozon** (`price_indexes` из `v5/product/info/prices`,
  компонент `LiveOzonCompetitorIndex`) — это агрегат «дороже/дешевле рынка»,
  который считает сам Ozon, а НЕ карточки конкурентов.

---

## 2. Проблемы текущего подхода

1. **Каждый поиск пользователя = живой запрос во внешний поиск.**
   `search.wb.ru` жёстко лимитирует по IP/частоте. При активном использовании
   (пресеты, несколько вкладок) — бан (HTML «429»).
2. **Нет общей очереди/троттлинга** для публичного канала (в отличие от
   кабинетного API). Запросы летят параллельно.
3. **basket-host формула захардкожена** (до `basket-21`). WB добавляет баскеты —
   фото/`card.json` для новых `nmId` начнут отдавать 404.
4. **Один IP.** Для масштаба (много запросов/клиентов) одного IP VM мало.
5. **Ozon-выдачи нет вообще.**

---

## 3. Целевая архитектура

Принцип тот же, что для кабинетного API: **«сбор» отделён от «чтения».**
Пользователь читает кэш; во внешние площадки ходит контролируемый сборщик
с очередью, троттлом и кэшем.

```
Браузер ──► /api/competitors/search?mp=wb|ozon&q=...
                │
                ▼
        competitorSearch(mp, q)                 (api/_lib/competitors.ts)
                │  1) cache hit (свежий) ─────────────► отдать
                │  2) miss → очередь per-host (троттл)
                │  3) парсер площадки (WB | Ozon)
                │  4) нормализация → CompetitorItem[]
                │  5) cache.set(key, ttl)
                ▼
        Фоновый прогрев (cron): топ-запросы клиента (PRESET_QUERIES)
        парсятся раз в N часов → пользователь почти всегда читает тёплый кэш.
```

### 3.1 Единая модель
```ts
type CompetitorItem = {
  platform: 'wb' | 'ozon';
  id: string;            // nmId (WB) | sku (Ozon)
  name: string;
  brand: string | null;
  seller: string | null;
  price: number;         // цена для покупателя (после скидок), ₽
  oldPrice: number | null;
  rating: number | null; // 0..5
  reviews: number | null;
  image: string | null;  // URL превью
  url: string;           // ссылка на карточку
};
type CompetitorSearch = {
  platform: 'wb' | 'ozon';
  query: string;
  fetchedAt: number;
  items: CompetitorItem[];
  partial?: boolean;     // часть данных не догрузилась
  error?: string;        // 'rate_limited' | 'blocked' | ...
};
```

### 3.2 Очередь + троттл (анти-бан)
- Последовательная очередь **per-host** (`search.wb.ru`, `www.ozon.ru`),
  пауза между запросами 1.5–3 с + джиттер.
- Кэш поиска: TTL **6–12 ч** на `(platform, нормализованный запрос)`
  (выдача за день почти не меняется).
- Дедуп: одинаковый запрос в полёте — один реальный поход (single-flight,
  как SWR в `_proxy.ts`).
- На 429/блок: отдать прошлый кэш (stale) + поставить cooldown на хост.

### 3.3 WB-парсер (доработка существующего)
- Источник: `search.wb.ru/exactmatch/ru/common/v9/search` (уже есть).
- Заголовки как у браузера (`User-Agent`, `Accept`); параметры
  `dest`, `appType`, `curr=rub` — оставить.
- Фото/карточка: `card.json` с `basket-XX`. **Починить вычисление баскета:**
  при 404 перебирать соседние баскеты или вынести таблицу диапазонов в конфиг,
  обновляемый по факту 404 (auto-bump).
- Уже есть защита HTML-429 — переиспользовать.

### 3.4 Ozon-парсер (новое)
У Ozon нет открытого `search`-API как у WB. Варианты по возрастанию надёжности
и стоимости:

1. **Composer BFF (рекомендуется первым):**
   `https://www.ozon.ru/api/composer-api.bff/page/json/v2?url=/search/?text=<q>`
   Возвращает JSON «виджетов». Парсить виджет `searchResultsV2`/`tileGridDesktop`:
   из него тянуть `sku`, название, цену, рейтинг, картинку, ссылку.
   - Требует браузерные заголовки и иногда cookie (`__Secure-*`).
   - Антибот агрессивный; на РФ IP мягче. На блоке → cooldown + stale.
2. **Headless (Playwright) как fallback:** рендерим страницу поиска,
   снимаем JSON из сети или DOM. Дорого по ресурсам, но устойчиво к антиботу.
   Запускать только когда BFF отдаёт challenge.
3. Если оба нестабильны — деградация: показывать Ozon-индекс цен
   (`price_indexes`, уже есть) как суррогат «позиции к рынку».

> Все Ozon-эндпоинты выдачи помечаем **[требует проверки]** — формат BFF Ozon
> периодически меняет имена виджетов; парсер должен быть терпим к отсутствию
> полей (как WB-парсер).

### 3.5 Масштаб / прокси (опционально, позже)
- Один IP VM хватает для одного клиента и фонового прогрева топ-запросов.
- Для многих клиентов/частых ad-hoc — пул **резидентных РФ-прокси**:
  ротация на хост, тот же троттл. Включается флагом `PROXY_POOL_URL`.

## 4. Эндпоинты (план)

```
GET /api/competitors/search?mp=wb|ozon&q=<запрос>&limit=<n>
    → CompetitorSearch  (из кэша; при miss — гейтованный парс)

GET /api/competitors/card?mp=wb|ozon&id=<nmId|sku>
    → полная карточка (описание, характеристики, все фото) для Claude Vision
```
Старые `/api/wb-public/*` оставить как алиасы на время миграции.

Фоновый прогрев в `handleCron`: пройтись по `PRESET_QUERIES` клиента
(CarPlay-адаптер, Android-магнитола, …) для WB и Ozon, разложить в кэш.
Так пользователь почти всегда читает тёплые данные и не инициирует бан.

---

## 5. Как это будет работать для пользователя
1. Открывает «Конкуренты», вводит запрос (или жмёт пресет).
2. Фронт зовёт `/api/competitors/search` — мгновенно получает кэш
   (прогрет фоном) или, при первом уникальном запросе, ждёт один
   гейтованный парс (≤ пары секунд).
3. Видит карточки конкурентов (цена/рейтинг/отзывы/фото), выбирает «нашу»,
   жмёт «Сравнить через Claude» / «Разобрать карточку» (Vision) — как сейчас.
4. Площадки не банят: реальные походы редкие, очередные, кэшированные.

---

## 6. Порядок реализации
1. Вынести WB-парсер в `api/_lib/competitors.ts` + единый кэш/очередь.
2. Новый `/api/competitors/*` поверх него; WB-выдача и карточка.
3. Починить basket auto-bump (устранить устаревание формулы).
4. Добавить Ozon-парсер (Composer BFF) с терпимым к изменениям парсингом.
5. Фоновый прогрев топ-запросов в `handleCron`.
6. (Позже) пул резидентных прокси под масштаб + headless-fallback для Ozon.
